# Requirements for generic weight-space programming

This document maps the reviewed source evidence and the repository's existing limitations to requirements, implementation boundaries, and acceptance evidence. It is a design inventory as of November 6, 2026, America/Chicago. It does not report a new experiment or treat an implemented interface as evidence that an editor can use it successfully.

The framework's intended scope is a common way to state and inspect **reading, diagnosis, editing, and creation tasks over weight artifacts**. General tensor storage, executable semantics, mathematical certification, and useful behavior are separate capabilities. A caller can add an architecture adapter without thereby obtaining a proof, an enforced access regime, or an empirical generalization claim.

The [source review](source-review.md) is the evidence entry point. Its [archive companion](../../../artifacts/weight-space/source-review-v2/README.md) records retained files, review coverage, provenance, and omissions. The review found no standalone limitations or next-steps document in the bounded source scan; the matrix below uses the actual report discussion and local sections. The [research and engineering program](limitations-and-next-steps.md) turns unresolved requirements into prioritized work.

## Reading the status column

| Status | Meaning here | What it does not mean |
| --- | --- | --- |
| **Implemented** | A named implementation or checked mathematical result provides the stated capability within the row's explicit scope. | Every caller uses it correctly, every premise is established, or an empirical hypothesis passed. |
| **Partial** | Some required mechanism exists, but an integration, enforcement, correspondence, coverage, or evidence obligation remains. | The missing obligation can be inferred from a nearby passing check. |
| **Open** | The required implementation or evidence is not established by the reviewed v2 material. | The objective is impossible or the source report has been disproved. |

These are capability and evidence statuses, not study outcome labels. In particular, an implemented runner, a frozen protocol, and a deterministic analytic constructor are not completed independent trials of a language model. References to the [v2 protocol](protocol.json) identify design commitments; numerical outcomes belong in a separately retained run and its results report.

Two historical boundaries have changed in v2. The older design's default registry was ReLU-only; the current [registry](../../../rlcd/weight_space/semantics.py) also registers the sequential backend. Feature coverage, executable correspondence, and numerical execution remain separate obligations. Historical files and results keep their original scope.

## Evidence required before making a claim

Requirements are conjunctive where a claim depends on several layers. A useful real-valued preservation claim needs exact candidate and semantic identities, valid premises and domain, a sound bound or equality, and an explanation of the runtime correspondence still trusted. A deployed numerical preservation claim additionally needs numerical execution evidence. A task-improvement claim additionally needs valid task metrics, independent held-out evidence, and a retention criterion. A live-LLM ability claim additionally needs a real provider trial, a declared information/computation regime, and the appropriate editor/checkpoint/task repetitions.

An acceptable record can contain a valid artifact, a checked nonzero residual, a loose semantic bound, a failed target objective, and a correctly selected no-op. Those are compatible observations. Keeping them separate makes the record more useful than replacing them with a single success flag.
